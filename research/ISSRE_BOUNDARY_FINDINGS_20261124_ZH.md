# 从公开契约选择调用边界：两个新项目的一轮封存验证

2026 年 11 月 24 日。**七条生成的边界契约都能执行，四种策略在十个封存历史提交对上均为 0/10。** 放开预算后，所有冻结输入的最终值和边界记录仍全部一致。揭示后的两个配对案例定位了不同原因：一个已经选到正确 API，但没有观察参与方的先后顺序；另一个已经选到正确接收者，但测试未构造值相等、身份不同的发送者。

## 样本与证据单位

Blinker 和 pluggy 均未参与此前的 attrs、Click、Rich 等实验。样本程序从默认分支可达的非合并提交中，按既有关键词、时间和运行库路径筛查。2023 年 10 月至 2025 年底，两项目各匹配五个，全部保留。设计者在揭示前可见数量。文档来自更早的 Blinker 1.6.2 和 pluggy 1.3.0，只对公开类方法说明进行匹配。冻结内容包括脚本、文档定位、期望、清单、预算与每组入选任务。本地单操作者封存的 SHA-256 为 68e230c6bbd58662f3e128f4b167e8c09dbc67f8f6dfaefec7273c0d01828ee8。[协议](ISSRE_BOUNDARY_PROTOCOL_20261124_ZH.md) · [冻结记录](../runs_contract_boundary_20261124/freeze.json)

十个分析单位是历史提交对。pluggy 的两个提交涉及同一上游问题 #544，另有一个提交标题为修正类型忽略注释；Blinker 含兼容导入、解释器关闭和对象身份方面的修订。十对均执行成功。本文不将其计作十种独立运行时故障。[机械抽样清单](../runs_contract_boundary_20261124/sealed.json)

## 核心算法与文档依据

程序从旧标签读取公开方法说明，在三个预选类上扫描有文档的非下划线方法。五种人工定义的语句模式识别事件转发、事后通知、延迟回放、临时参与、调用前后监测。匹配后绑定触发动作、记录器及应读字段，用项目适配器构造两种输入，并将实际交互与预期记录比对。两项目共检查 37 段，匹配 7 条，生成 14 个输入。模板与项目适配器由研究者阅读这批文档后编写。这次检验的是对未知修复的适用性；没有评估把模板原样迁移到未读文档的效果。37 段未做全部可测试契约的人工金标准标注，不能计算抽取召回率。

| 文档条款 | 公开动作与检查点 | 本轮绑定的预期 |
|---|---|---|
| Blinker receiver_connected | 连接接收者，监听连接通知 | 通知来源为该信号；参数保留接收者、发送者与 weak 设置 |
| Blinker receiver_disconnected | 显式断开，监听断开通知 | 来源为该信号，传入的接收者和发送者一致 |
| Blinker send | 同步发送，记录接收者入参 | 实际发送者与业务关键字参数传递一致 |
| Blinker send_async | 异步发送，记录协程接收者入参 | 接收者获得对应的发送者与关键字参数 |
| pluggy call_historic | 调用后注册插件，记录结果回调 | 对非空插件结果触发对应回调 |
| pluggy call_extra | 临时加入方法，再次普通调用 | 临时方法得到指定参数，普通调用中退出 |
| pluggy add_hookcall_monitoring | 安装前后监视器并执行，可撤销 | 检查调用阶段、关键字参数、结果与撤销后的记录 |

这七项分别按旧文档原文核对了主要语义。预期值中的具体常数来自测试夹具。同步与异步 send 的解释还使用旧文档 connect 对发送者与接收者形参的说明；这项跨段依据由人工核对，程序只保存了匹配段落的定位。没有独立第二人标注。正则匹配本次分别花费 0.512 和 0.149 毫秒；读取 Git 文档、解析、匹配和产生条款合计分别为 37.26 和 65.64 毫秒。人工定义规则和适配器的工时未单独计量。[抽取记录及定位](../runs_contract_boundary_20261124/contracts.json) · [Blinker 文档所在旧标签](https://github.com/pallets-eco/blinker/blob/1.6.2/src/blinker/base.py) · [pluggy HookCaller](https://github.com/pytest-dev/pluggy/blob/1.3.0/src/pluggy/_hooks.py) · [pluggy PluginManager](https://github.com/pytest-dev/pluggy/blob/1.3.0/src/pluggy/_manager.py)

未优化契约组与组合输入组使用相同请求顺序，前者读取边界，后者读取最终结果。常规组使用同批规则中的普通输入。该设计给最终值基线同样的 API 入口知识，有利于比较增加观察器的边际贡献。优化组枚举至多三项输入，在参考时间和调用上限内，最大化不同的“观察器、字段”以及“动作、条件”覆盖数；并列时取预计执行成本较低的集合。各方法每项目最多三个场景、十五个协议计费操作，并共用参考时间上限，Blinker 为 29.55 微秒，pluggy 为 171.75 微秒。解释器、导入和下载不计入，装配与验证的墙钟费用计入。超时调用允许返回，越过截止的结果不予计分。[生成和执行规则](issre_boundary_probes.py) · [预算与计划](../runs_contract_boundary_20261124/schedules.json)

## 两个揭示后的配对诊断

**pluggy 已经执行了 call_extra，漏掉的是相对顺序。** 冻结测试记录临时方法收到的参数及参与范围；它没有注册包装器，最终结果还按值排序。揭示后增加公开包装器，让临时方法和已注册方法都返回 9，以便把最终值与事件顺序分开观察。没有包装器时，加优先标记也未产生版本差异。加入包装器后的实测如下，选用普通优先级。

| 观察 | 父提交 | 修复提交 |
|---|---|---|
| 最终返回 | [9, 9] | [9, 9] |
| 调用轨迹 | 临时方法 → 进入包装器 → 注册方法 → 退出包装器 | 进入包装器 → 临时方法 → 注册方法 → 退出包装器 |

上游回归测试记录了相应的顺序要求。冻结解析器略过下划线方法，包装器顺序的公开说明恰好也见于 HookimplMarker 的调用接口及使用指南。单段匹配没有把“临时参与”与“包装器应包围参与者执行”两个条款组合在一起。该诊断由修复材料引导，只计作事后见证。[上游修复及测试](https://github.com/pytest-dev/pluggy/commit/443fee6d7a30ca694aa2eec77bde4aea9356efa0) · [修复前使用指南](https://github.com/pytest-dev/pluggy/blob/1.3.0/docs/index.rst)

**Blinker 的差异用最终返回即可看到。** 在接收者上登记一个整数作为发送者，重用同一对象，两版均返回 [9]。换成另一个数值相等的整数对象后，父提交返回空列表，修复提交返回 [9]，父提交的接收者没有执行。冻结任务一直使用原发送者对象。具体整数匹配的期望由揭示后的上游回归测试核实；旧文档只写明可以指定发送者，没有在所匹配段落中说明整数身份与数值相等的区别。[上游修复及测试](https://github.com/pallets-eco/blinker/commit/e27fc051ed0338e76ee967d4bdcf16527d84f4ce)

这两例分别给出一个充分条件的证据；其余八个提交未作逐项因果复现。两例均未加入盲测成绩。

## ISSRE 研究结论

这一次独立验证已结束。七条条款支持“用规则从某些公开描述编译出可运行的交互观察器”，十个历史提交对没有提供“这种编译提高了独立修复检出率”的证据。沿用 ISSRE RES 实证主线与 ESEM 备选，将本轮作为有强基线和留出参考版本的负结果。稿件可用 attrs 初始化参数、Click 关闭回调、pluggy 包装器顺序与 Blinker 整数身份展示不同的改进措施，并逐一注明证据来自盲测还是事后诊断。避免将预算外菜单无见证的场景计为选择策略失败。

已有研究分别从形式契约生成测试、为 REST API 生成判据；RIPR 模型讨论到达、状态感染、传播与揭示。本文可直接交付的增量是有限预算与公开观察权限下的可执行配对证据，以及输入、观察位置与时序判据之间的区分。当前结果支持继续写实证论文。若未来重新开启方法分支，先用独立材料验证能否从跨段契约推导出参与方之间的先后关系，再考虑优化预算。[形式契约生成测试](https://doi.org/10.1016/j.infsof.2024.107467) · [REST API 判据生成](https://homes.cs.washington.edu/~mernst/pubs/rest-oracle-tosem2025-abstract.html) · [RIPR 教学原图](https://www.cs.cornell.edu/courses/cs5154/2021sp/resources/TestingConcepts-1.pdf)
