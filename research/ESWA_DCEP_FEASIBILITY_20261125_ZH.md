# 一次验证该用在哪里？DCEP 发布清单工作流可行性实验

2026 年 11 月 25 日

**研究决定。** 保留“验证结果是否改变最终行动”这一评价方法。本轮可把 DCEP 作为精确规划的实验原型归档。原生批量检查逐项复现了 DCEP 的 320 个交付决策，且本次实测更快。现有证据不足以把 DCEP 推进为 ESWA 的核心算法。

## 任务与比较单位

本地发布助手持有上一次发布的文件清单。用户要求交付当前发布版的源码清单、测试清单、源码加测试，或源码加测试加示例。每行必须包含准确的相对路径、文件模式和 Git 对象标识。助手可读取一次版本证据，随后决定复用、重建哪些目录或暂缓。交付实际写入 JSON。评分器以独立的 Git 递归清单核对整个文件。

用 tqdm 的 40 个不重叠父子提交对校准，用 transitions 的另 40 对评估。每对使用相同的旧清单，分别把父版本、子版本作为当前发布状态。总计 40 对 × 2 状态 × 4 个请求模板 = 320 个留出情形。发布状态配比及用户请求为受控设计。真实提交、对象读取和交付文件均来自实际执行。项目间留出考察同一工作流，未测独立用户、第二种工作流或语言模型自主编排。

每个端点均可使用同一进程内的精确对象缓存。查一个目录与批量查三个目录都可从同一个根树对象取证。一轮内缓存供随后重建复用。预算为交付前至多一次逻辑检查；另计实际 Git 对象读取，覆盖验证和交付。上次已发布清单和长期运行的本地 Git 对象服务是共同初始条件。部署耗时从策略决策计至交付文件写完，含规划、读取和写文件；开发集校准、历史快照准备及离线评分单列于流程之外。本次单机交错计时未估计机器间时延差异。

## 核心算法与可验证的剪枝条件

状态用三个布尔量表示源码、测试、示例的清单是否变化。请求指定所需目录集合 Q，行动指定重建集合 A。若变化集合 S 与 Q 中任何未重建目录相交，交付有误。依赖图为“目录对象 → 目录清单 → 用户请求的字段 → 交付损失”。在本实验的契约下，目录外的修改不直接改变被交付的字段，但它仍可能通过与其他目录修改的相关性提供信息。

规划器在开发集估计八种变化状态的频率，做加一平滑，并实测检查、冷重建和检查后热重建的中位耗时。两种规划器共享这些估计。它们在“当前直接行动”和“读取证据后分支行动”中最小化期望损失。损失包含实测耗时模型与预设的错误代价 10 毫秒等价单位、暂缓代价 5 毫秒等价单位。后两项是实验偏好，未经用户成本校准。

DCEP 在标准单步信息价值规划上做两项处理。

1. **按最终行动损失合并状态。** 先按探针实际可能返回的结果分组，再在每个分组内把 S 与 Q 交集相同的状态合并，累加概率。对每个允许行动，这些状态的错误损失相同。这种次序保留了其他目录变化所携带的统计信息。
2. **删去受支配的探针。** 若批量探针能推出单目录探针的全部结果、留下相同的后续缓存且成本不高于单查，则批量探针可模拟单查的任何决策。在这些条件下可以删去单查。本次校准中批量端点没有达到成本条件，实际删去 0 项。

算法允许在当前最优行动的损失已不高于所有检查方案时停止。校准采用点估计。本轮没有实现跨项目的统计置信界，状态等价与支配关系只对规定的任务模型成立。单步规划也没有对必须组合两次检查才有价值的情形给出结论。

## 留出结果

每行分母 320，所有策略的暂缓数均为 0。单位为本次 320 次请求的本机累计毫秒。缓存规划策略只按四种公开请求模板缓存决策树，每次仍读取当前版本证据。固定与风险基线获取所选证据后，均可用相同概率模型决定重建范围。

| 策略 | 正确 | 错误 | 检查次数 | Git 对象读取 | 规划 ms | 决策至交付 ms |
|---|---:|---:|---:|---:|---:|---:|
| 直接复用旧文件 | 233 | 87 | 0 | 0 | 0.62 | 100.67 |
| 直接重建全部请求目录 | 320 | 0 | 0 | 1,279 | 0.72 | 179.22 |
| 风险决策，无验证 | 320 | 0 | 0 | 1,279 | 7.93 | 184.31 |
| 固定查源码 | 320 | 0 | 320 | 826 | 14.79 | 168.51 |
| 最大结果熵 | 320 | 0 | 320 | 545 | 28.65 | 172.49 |
| 普通风险排序＋精确缓存 | 320 | 0 | 320 | 758 | 16.26 | 171.21 |
| 原生批量检查，重建变化目录 | 320 | 0 | 320 | 545 | 1.13 | 141.24 |
| 标准信息价值规划 | 320 | 0 | 320 | 545 | 35.43 | 180.94 |
| DCEP | 320 | 0 | 320 | 545 | 43.54 | 184.77 |
| 缓存标准规划 | 320 | 0 | 320 | 545 | 0.97 | 151.66 |
| 缓存 DCEP | 320 | 0 | 320 | 545 | 1.09 | 142.20 |
| DCEP 选择同一检查，屏蔽反馈 | 320 | 0 | 320 | 1,279 | 45.86 | 227.80 |

**检查位置影响成本。** 固定查源码和风险排序同预算、同正确数，分别读取 826 和 758 个对象。直接重建达到正确交付上限。盲读与 DCEP 对照把检查身份和缓存预热都保持一致，读取返回值后少读 734 个对象，且有 277/320 次最终行动发生改变。决策结果的区别体现为复用和局部重建。

**同一请求的实时证据确实有增量。** 用“发布前后成对比较”这一更严格的口径，160 个同任务、同旧清单、同探针的配对中，有 87 对改变最终行动，分布于 28/40 个版本转换。这个分母与“277 次不同于无反馈决策”回答的是两个问题。

**强基线解释了全部交付收益。** 标准信息价值规划与 DCEP 的探针、行动、对象读取逐项相同。原生批量检查与 DCEP 选了 160 次不同的检查，但 320 次行动全部相同。DCEP 将未缓存规划中的状态—行动损失求值从 64,000 降至 54,080，减少 15.5%，构建分组的开销使规划总时间从 35.43 增至 43.54 毫秒。模板缓存把两种规划都压缩为四次实际求解。缓存版之间的单次计时差不足以认定稳定加速。

## 一例发布前后配对

旧清单来自 transitions 提交 e3015425，下一发布提交为 c220cfa1。用户要求源码、测试与示例三份清单。两个状态下均执行相同的根目录检查。发布前，三项目录标识均相同，复用清单共读一个 Git 对象。发布后，仅测试目录发生变化，只重建测试，共读两个对象。两份交付均正确。屏蔽返回值时，要保证这项任务的正确性，校准模型在本例选择三项目录全部重建。原生批量规则也找到同一个局部重建行动。

## 研究取舍与相关工作

本轮通过了“证据改变行动”和“在相同正确性下少读对象”两道门槛。它同时给出了一个决定算法投入的条件：如果工具用一次廉价读取即可报告所有相关变化，而且反馈直接决定最小修复动作，复杂的检查选择缺少收益空间。

在有明确业务来源的工作流中，只有出现互不包含的检查、不同的修复路径和真实测得的检查成本，才值得重开 DCEP。届时先用全部可部署的简单方法和精确规划测量可改善空间，再决定是否投入置信界或多步搜索。当前数据支持的是本地发布清单的工程结论。CASEL 已研究后果感知的执行与验证分配，Anytime Verified Agents 已使用信息价值分配验证计算，本轮没有针对两篇论文原系统进行复现或宣称超越。[CASEL](https://arxiv.org/abs/2610.36570) · [Anytime Verified Agents](https://openreview.net/attachment?id=JMDCMf7mlF&name=pdf)
