# 规则库可能不完整时，第三次调用能否阻止错误采用？

2026 年 11 月 23 日 · TinyAgent 本地日历接口实验

**本轮决策：优先推进错误采用与反证测试的可靠性研究。** 允许反证器调用更丰富的组合解释后，同一批程序前二候选的错误采用从 13/216 降到 0/216，代价是额外暂缓了 7 个原本能正确采用的场景。相同三次调用下，直接搜索 1,106 种规则的程序正确确认 184/216、错误采用 0 次，每场景 CPU 中位耗时 5.50 毫秒。0.6B 没有带来正的净识别收益。

## 实验对象

复核上轮原始记录后，新造 24 个独立布局，每个布局运行九种黑盒接口，共 216 个场景。每个布局的首个日程由相同种子生成，九种接口共享输入，首次返回由各自的实际行为决定。第一条返回有可能与旧工具看起来一致。布局有两套字段名；进入本轮提案器之前，都标准化为 ID、时间、所有者、状态与优先级。算法能看见完整校准日程，但看不到接口类别、真实规则、种子和留出答案。

| 真实接口 | 每类场景 | 实际行为 |
|---|---:|---|
| 单一操作 | 72 | 分页前按 ID 去重、分页前排除一个状态、主时间相同按优先级降序 |
| 组合操作 | 72 | 排除某状态后按所有者去重再分页、二级排序并分页后过滤、二级排序并分页后按 ID 去重 |
| 原组合库之外 | 72 | 跳过首条后取三条、每隔一条取一条再分页、按时间列表反向取三条 |

小库有 16 种单操作管线。将三类操作各选零或一个，再枚举它们与分页的顺序，得到 1,082 种不同语法的管线；库内包含语义重复的写法。第三个全搜索对照额外加入 24 个切片模板，共 1,106 种。库外场景的三种行为可用切片表达。模型的自由输出允许写入未在模板中出现的切片参数，受语法约束的提案则从扩充后的语言中解码。因而即使受约束提案命中库外真值，也要与廉价的程序切片扩展直接比较。

用一份按不同时间排列、所有 ID 与所有者均唯一、状态均相同的日程，可以严格区分三种切片行为和原组合库。去重与二级排序在这份日程上不改变任何记录；过滤只能保留全部或删除全部。无论如何排列这些操作和分页，结果只能是前三条或空列表。三个切片接口分别给出其他序列。

## 决策与核验

- **程序前二**先按首条反例对 16 个单操作打分，由前五个不同编辑构造至多 40 个有序组合，再按首页长度差和位置差排序，保留两条。**不同族前二**要求第二条的首个非分页操作属于不同族。两候选表示进入主动验证的数量，初筛、额外核验和模拟探测的计算都计费。
- **固定混合**保留程序第一名并加入一个不同的模型提案。冻结 P11 Qwen3‑0.6B 使用同一首条轨迹做自由生成和宽度为二的受约束生成，自由提案有效时优先，去重后最多留下两个备选。提示没有提供预测表、候选得分或真实接口类型。
- **门控**用真实首页排除已经被反例推翻的候选。对其余候选，在未来的公开测试日程上比较替换前后能解释的不同返回。只有模型解释符合首页、不会丢掉现有候选覆盖的任何预测返回，并且在合计至少两个“日程、返回”组合上增加覆盖，才允许替换。阈值是本次设计选择，增加预测覆盖并不保证增加正确率。纯程序门控分别使用排序靠后的两个程序候选，或把 24 个切片按实际首页拟合度排序后的前两名。
- **三次真实调用**依次为原始日程、第二次校准、第三次反证。第二问在八个随机新日程中选择，使旧规则和存活候选的预测尽量分开。第三问还可使用构造的同所有者不同 ID、同 ID 不同所有者、时间相同、同状态等日程。普通策略继续最大化当前候选的分歧。主动反证额外寻找不在最终候选中、却仍能解释前两次返回的单操作规则，选择能让它们与领先解释产生最多分歧的日程。
- **暂缓采用**适用于零个解释存活，或存活解释在公开探测日程上仍有可见分歧的情况。风险门控还要求通过第三问的挑战规则与拟采用的解释在公开日程上没有剩余分歧。挑战规则能否决采用，没有资格被自动补为最终答案。全搜索方法会合并在全部公开探测日程上行为一致的候选。
- **留出识别**要求所采用规则在独立随机与构造日程上全部返回正确且有序的 ID。不同写法如具有相同行为可得分；这是一项行为识别率。Recall@2 同样按行为计算，全搜索对应的是全库覆盖率。错误采用率和暂缓率均以全部场景为分母。每个布局的九种接口一起重采样，做 10,000 次配对布局自助抽样，区间描述这批布局的波动。

## 主结果与成本

下表各组分母均为 216，各用 648 次本地黑盒校准调用。覆盖表示保留的候选中至少一条与真实接口在全部 43 份离线验收日程上行为一致。前二方法报告 Recall@2，全搜索列给出相应库覆盖。CPU 时间是单场景进程 CPU 时间中位数，包括采样请求规划和模拟规则执行，不含模型推理、启动、留出评分或远程网络延迟。规则评估数按每个策略在单一场景实际执行的不同“规则、输入”组合计，策略内部可复用预测。成本值来自同一台机器的一次完整计时运行。

| 同一风险门控，备选来自程序排序 | 73 | 73 | 13 | 130 | 111.6 | 0.454 |

扩大完整规则库后，三个层次的正确确认依次为 62/72、50/72、72/72。库覆盖 216/216 而正确确认 184/216，剩余 32 个场景在三次调用后仍有可辨认的不同解释。16 条小库比程序前二更省 CPU：直接遍历小库，比先搜索若干组合再选两条更便宜。两候选限制在这里没有实用成本依据。若容许约 5.5 毫秒本地计算，扩充后全搜索是本轮表现最好的方法。

### 模型有没有补进缺失的真实规则？

216 个场景中有 170 种不同的公开历史。按相同输入共享推理，主面板模型实际输入 86,798 token，输出 6,596 token，批处理生成累计 65.0 秒，不含加载及分词。按每个场景单独摊计，每个模型策略对应 110,344 个输入 token、8,327 个输出 token 和约 82.0 秒模型时间；各策略共享同一份提案，实际没有重复发生这笔开销。程序策略模型 token 为零。

在本轮文本格式约定下，自由生成没有产出一条可直接解析的完整管线。受约束生成的 432 个候选中，有 384 个以切片开头、43 个以二级排序开头、5 个以去重开头。最常见的候选对出现在 128/216 个场景中，两个候选都是从列表开头附近向前切片。216 个场景里没有任何一组模型候选在留出日程上实现了真实行为，72 个库外场景的正确补全也是零。程序切片补全则单独挽回其中 53 个。门控一共接受了零个模型替换：相比无条件混合多保住 19 个正确确认（+8.80 个百分点，布局配对 95% 区间 +6.48 至 +11.11），与程序前二逐场景打平。

另在上轮原始 24 个场景上诊断操作族偏置。原提示加束搜索的 48 个候选全是过滤。保持检查点、反例与解码语法不变，只反转操作说明顺序，得到 43 个过滤、5 个去重；保持原提示，将束搜索换成固定随机种子的两次受约束采样，48 个仍全是过滤，组内去重后剩 43 个不同提案位。三种条件都只在 5/24 个场景命中真值。说明顺序有影响，单独改顺序或该采样策略都未解决集中于一族的问题。新语法中偏好转为切片，同时变化的还有任务、语法和提示，尚不能归因于其中某一项。

### 哪种反证能减少错误采用？

程序前二的 13 个错误全部来自组合接口。只用通过前两次返回的单操作规则挑战候选，13 个错误全部保留。主对照完成后，将可挑战的范围扩至 1,082 种组合，保留相同的两个可部署候选与三次调用预算。原先 13 个错误采用全部转为暂缓：12 个在新的第三问上没有候选存活，1 个被仍符合证据的竞争解释否决。另有 7 个原可正确采用的场景一并暂缓。错误采用率差 −6.02 个百分点（布局配对 95% 区间 −9.26 至 −3.24），正确确认率差 −3.24 个百分点（−6.02 至 −0.93）。在同一面板上作的后续诊断，需在新的接口族上评估能否复现。

例如，场景 1-compound-1 真正在主时间相同时还按优先级排序，分页后再过滤。程序原先采用了“分页后过滤”。新的第三问中，简化规则预测 O、E、O，真实返回 E、O、O；即使 ID 集合完全相同，次序上的反证也足以拒绝部署。上轮的 owner/uid 错案也用实际本地调用复核：放入两个不同 ID、同属 Alice 的事件，原采用规则预测返回两个，工具只返回第一个。

### 库里没有真值，而且普通请求永远测不出差异时

再构造一组独立的机理对照。在按 ID 去重、按状态过滤两类服务中，各有一个稳定版本和一个只在输入超过十条时切换规则的版本。越过阈值后分别改为按所有者去重、排除另一状态。每个布局使用两个版本完全相同的前两问，并固定要核验的领先解释，单独测第三问。普通第三问有七条记录；反证第三问只在同一日程末尾增加七条更晚的记录，稳定解释的前三条预测保持不变。

| 真实服务 | 七条输入：采用 / 错误 | 十四条输入：采用 / 错误 | 十四条输入：暂缓 |
|---|---:|---:|---:|
| 稳定规则（48 个场景） | 48 / 0 | 48 / 0 | 0 |
| 超过十条切换规则（48 个场景） | 48 / 48 | 0 / 0 | 48 |

这项构造控制了改变的因素，验证的是第三问能否推翻一个稳定性假设。测试维度由实验者选择，算法并未自主发现十条阈值，也没有恢复阈值后的真实规则。在服务只允许读取长度不超过十条的输入时，这对接口对所有允许请求的输出都相同，增加同类调用次数也无法区分。

## 研究决定

下一轮用完全留出的失效类型检验**如何选择反证维度**。冻结已知规则库和请求构造器，再加入未参与设计的接口变化，分别在只能查询现成日程与能构造测试日程两种权限下比较。主要对照应为相同 CPU 时间与 API 调用预算下的完整程序搜索、程序化反证和模型建议反证。先比较在相同正确采用覆盖率下谁能更少误判，再看模型是否提出了程序确实遗漏的测试输入。当前支持将成果定位为有限查询下的错误采用诊断与评测；现有成绩尚不支持给模型固定分配候选位。
