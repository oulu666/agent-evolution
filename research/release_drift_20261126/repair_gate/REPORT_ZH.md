# 识别违约之后，什么能把暂缓变成正确交付？

**2026 年 11 月 26 日。** 上轮公开实验留下两份无法交付的 XlsxWriter 工作簿。两份都已准确检出列可见性违约。本轮只改变是否允许一次经验证的本地修复，并在两种动作集内比较四种判断方式。修复使正确交付从 78/80 升至 80/80；在任一动作集内，更换判断方式均未改变任何一次交付。

## 方法与实际产物

复用原 40 种编辑序列，在 3.3.0 和 3.3.1 两个发布版本各生成一次真实工作簿。由于上轮只归档了可见性与文字，需要重新生成二进制产物才能验证修复。每个首次观察均与上轮同版本同输入记录一致。四种方法共用该工作簿、当时的文本和可见性要求、评分器与首次请求后最多三次额外调用的额度。云端按版本并行，各版本内并行评估各臂。

* **静态强基线**沿用原判据，直接核对指定列可见和 A1 文字。
* **A 证据约束契约编译**把人工从原任务转写的两条受控语句编译为含来源、字段及预期表达式的检查；限定操作域沿用原任务包。语法及字段绑定均由开发者给定。此次只验证该小词表能否执行，自动阅读自由文档的能力仍待验证。
* **B 反事实义务验证**枚举两项义务共四种真假组合，以实际文件字段排除矛盾解释。在 80 项中均只剩一个组合。这里检验的是对当前产物的逻辑解释，未把枚举出的组合计为真实服务故障或真实探针返回。
* **C 主动选问准入**检查 B 的剩余解释是否对该任务给出相反判定。触发数为 0/80，实际追加探针为 0。C 行反映其共用 B 判据后的交付结果；对真正触发的主动选问没有可评价样本，本轮没有实现或验证通用多步算法。

## 配对结果

| 方法 | 原动作集：正确 / 错误 / 暂缓 | 允许局部修复：正确 / 错误 / 暂缓 | 误报 / 漏判 | 额外探针 |
| --- | --- | --- | --- | ---: |
| 固定产物检查 | 78 / 0 / 2 | 80 / 0 / 0 | 0 / 0 | 0 |
| A 编译判据 | 78 / 0 / 2 | 80 / 0 / 0 | 0 / 0 | 0 |
| B 反事实义务验证 | 78 / 0 / 2 | 80 / 0 / 0 | 0 / 0 | 0 |
| C 准入与共享判据 | 78 / 0 / 2 | 80 / 0 / 0 | 0 / 0 | 0 |

80 项来自一个真实历史修复；两项原始违约均在旧端。两个修复任务、78 个原本正确任务分别构成漏判和误报的分母。新端 40 项均直接交付。开关修复后的逐项差异正好是两次暂缓变正确，没有新增错误、误回退或其他交付改变。按损失 0/1/5，每臂累计损失从 2 降至 0。两组本来都能阻断错误，本轮独有的增益是实际恢复用户产物。

## 修了什么，以及如何复核

错误分别由“设列宽、写文字、自动调宽”和“写文字、设列宽、自动调宽”触发。两份旧产物中的 A1 都是 `hello world`，A 列宽度也同为 `11.140625`，但其列定义带有 `hidden="1"`。修复程序仅在目标定义精确覆盖 A 一列时清除这个属性。独立读取器 openpyxl 3.1.5 对交付物复查列可见性、文字和正列宽。各 ZIP 部件中只有目标工作表的内容改变；在修复后 XML 中重新补回原属性，规范化的工作表 XML 与原件相同。未进行 Excel 图形界面渲染评价。

两次本地修复和主判据回读分别耗时 2.72 ms、2.28 ms，共约 5.00 ms；不含独立评分、初始工作簿生成及运行环境准备。物理修复按产物复用，各方法在实际使用修复时均承担同一成本。计时用于说明实际工作量。

## 研究取舍

该案例支持把“已经判错、但缺少恢复动作”作为独立失败机制。对这一已知故障，直接检查与共享的局部修复已能完成登记任务；A 相对静态基线新增检出为零，B 没有遇到实际歧义，C 未遇到需要追加信息的输入。修复是依据已知公开故障人工设计的，收益不能归为自动合成修复或跨项目泛化。

正式四项封存变化、冻结窗口、共用判据和调用额度均未改变。开发侧的下一道选择是从已有公开失败中寻找**两个独立可观测结果一致、但当前任务结论仍然不确定**的案例，或找到**已有条款却无法自动绑定**的实际例子。前者可用于检验 B，以及存在合法中间反馈分歧时的 C；后者可用于检验 A。保留强基线能解决的样本作为对照。
