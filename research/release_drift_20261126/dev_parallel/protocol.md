# 开发实验：额外探针能增加版本证据，也能改善当前交付吗？

2026-11-26，执行前登记。使用已公开的 XlsxWriter 列可见性、时长格式和 Babel 周历年三个历史修复，两项目六个版本端点。复用既有 40、6、20 个用户输入；对每个端点先执行一次真实请求，并在各臂共享观察。旧版以缺陷对照运行，新版为修复端。研究单位为三个历史变化。Pillow、pandas、SciPy 的封存样本不参与。

候选一根据信息增益，从剩余的开发版本解释中选择区分力最大的请求，再依据返回收窄解释。候选二先计算当前交付的契约违约及可恢复性；完整任务判据在第 0 步已经可用时，任何纯识别探针都不能进一步降低终端损失，因而可直接停止或恢复。判据和处置对各方法相同。本轮检验两个目标能否在真实运行中导致不同的调用量与交付结果，以及强静态方法能否完全解释收益。

对照包括裸交付、固定前三个开发回归探针加 Schema、相同校准信息下的最优预排、固定种子的随机探测、固定只检查首个产物、直接走可用备用路径。最优预排枚举 0 至 3 个不重复请求，以最小剩余解释数、最少调用数及字典序选序列，允许共同提前终止；固定检查首个产物也是任务损失目标的强静态对照。四个候选探针与目标输入分离，每个端点执行四次形成公开开发校准库，成本另列。两端等权。每一臂至多三次额外调用，含在线恢复。版本探针只有直接看到与旧端不同的返回才登记版本差异。此指标按当前任务与旧端输出是否相同再分解。

周历年依据 Python ISO 日历核对完整标签，备用为已有离线日期算法；时长依据天数和单元格格式核对真实生成的工作簿，备用通过在线写入数值单元格生成新工作簿；列任务只要求指定文本和列可见，无已注册备用。交付仅按上述可观察要求评分。完整判据在本批例子上可用；不屏蔽判据制造主动方法获胜的机会。先检查当前产物，已确认违约则优先处置。对备用策略另记执行成本，裸交付用作直接执行参照。若主动与预排同分则保留较简单解释；额外识别另一个输入上的版本变化不能算作保护用户任务。

三个案例在 GitHub Actions 免费 CPU 并行，各方法用独立进程并发。登记逐请求原始返回、用户任务、基线旧端比对、预算、恢复结果、产物检查及各类耗时。并发用时仅供复核，不排名。此次属于开发验证，不能作为独立升级盲测或 ESWA 的方法优势证据。
