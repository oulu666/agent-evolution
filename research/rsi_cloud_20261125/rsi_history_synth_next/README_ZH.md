# Click 真实版本：固定菜单之外的合法测试能找到一个明确的语义差异

用 Linux 云端 CPU 和 Python 3.12 调用 PyPI 发布的 Click 8.3.3 / 8.4.0。两个解释器的 CLI 工具都用同一公开 API 构造，且确认实际加载路径及版本号。根据上游 [Click 8.4.0 变更记录](https://click.palletsprojects.com/en/stable/changes/#version-8-4-0) 预先选出两项已知变更。这个面板不是盲测，12 个参数值变体不是 12 个独立缺陷。

## 机制与同预算对照

**等价变换扩展**：固定菜单枚举同一种接口通道下的参数。实验在任务明示的语义等价关系内生成新测试，例如将环境变量里的合法文本表达与配置映射组合，测试“同一个整数对、不同配置通道”。也测试不改变业务语义的选项声明顺序轮换。生成器只使用预设任务契约，不查询版本源码或结果来构造测试；算子由设计者针对这两个任务先行登记，不能称为任意 API 上的全自动迁移或新颖算法。

判据独立于新旧 Click：坐标点必须等于预先给定的整数对；没有 argv 选项时应选唯一显式默认值，有则选最后一个命令行标志。只有旧版违反判据且新版满足才计中。所有策略使用相同预算（最多 2 次成对比对，每对包含两个库调用）；专家上限只给 1 个候选。展开菜单穷举另计。通过四个独立解释器执行完整组合，策略按各自顺序确定性离线重放，表中次数按策略实际检查的配对数计，不包含穷举表构建。独立同版本两次进程回放无虚假窗口；未主张畸形输入的行为。

| 策略 | 配置整数对（检出/12） | 共享默认值（检出/12）| 两任务总探测对数 |
|---|---:|---:|---:|
| 固定菜单，最多 2 对 | 0 | 0 | 48 |
| 固定菜单穷举 | 0 | 0 | 264 |
| 朴素扩展顺序，最多 2 对 | 0 | 0 | 48 |
| 同一完整文法，均匀随机，最多 2 对 | 7 | 0 | 44 |
| **等价变换优先，最多 2 对** | **12** | 0 | 36 |
| 已知变更的手写检测 | 12 | 0 | 24 |
| 完整展开文法穷举 | 12 | 0 | 600 |

复核配置正例：应用定义 `--point` 接受两个整数，固定菜单可检索 argv、环境字符串及已转换成整数元组的 `default_map`，均正常。允许调度器跨通道复用同一表示后，`default_map={"point": "1 61"}` 在 8.3.3 退出码 2 且报告值必须可迭代，8.4.0 退出码 0 并给出 `[1, 61]`，符合应用的独立判据。完整展开含 240 个测试对：旧版符合其中 144，新版符合全部。更改对应上游 [#3364](https://github.com/pallets/click/pull/3364)。这说明旧版不能满足新订应用契约，不声称旧文档保证这种配置合法。

共享默认值的零结果保留：两版对登记的 360 对全部满足判据，无须修复。本面板的三个文本模式开关与 [#3403](https://github.com/pallets/click/issues/3403) 原始布尔开关问题并不等价，零结果不能否定上游修复。

**判断：** 在配置语义契约的一个实际变化上，扩展覆盖了固定菜单不具备的测试表达力；统一的预设优先级快过同文法随机，但没有超过看过发行记录的手写规则。这批证据只支持“先筛查固定菜单的盲区”，不支持稳定进步或核心算法立项。下一步需要独立选取项目与任务、先冻结等价变换的选择机制，并对比同信息强基线。

## 复跑（只需要 Python 3.12 和两个 PyPI wheel）

```sh
mkdir -p wheels releases
python3 -m pip download --no-deps --only-binary=:all: -d wheels click==8.3.3
python3 -m pip download --no-deps --only-binary=:all: -d wheels click==8.4.0
(cd wheels && sha256sum -c ../WHEELS.sha256)
sha256sum -c LOCK.sha256
for ver in 8.3.3 8.4.0; do
  python3 -m zipfile -e wheels/click-$ver-py3-none-any.whl releases/click-$ver
done
python3 -B scout.py releases | diff -u aggregate.json -
```

### 揭盲后的修复验证（不计入冻结见证实验）

另外用版本隔离进程验证了两种应用兼容修复：由应用声明的整数元数自动生成配置字符串归一化器，以及直接手写解包并转两次整数。两者均把字符串转换成库接受的整数元组后交给 Click，不修改 Click 本身。16 个文本、已类型化列表、负数、空白与格式错误条件中，原生 8.3.3 为 8/16、原生 8.4.0 为 16/16；自动生成和手写规则在两个版本均 16/16。说明确实有合法兼容修复，但这不是新算法优势。覆盖的是声明范围内的数字与空白，不代表 Click 所有默认值形式。复现：`python repair_verify.py releases`。验证脚本是在看过版本差异后添加的。
