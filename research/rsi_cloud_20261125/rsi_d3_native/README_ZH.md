# D3：真实 wcwidth 版本上的联合收益与原生上界

在云端对 PyPI 发布的 wcwidth **0.2.14 / 0.3.0** 运行独立 Python 解释器。0.3.0 引入公开参数 `ambiguous_width`。见[上游版本历史](https://wcwidth.readthedocs.io/en/latest/history.html)和[使用文档](https://wcwidth.readthedocs.io/en/latest/intro.html)。实验定义一个普通功能任务：按两个终端面板各自明确声明的宽度配置，把两列日志标签补齐到固定宽度。独立判据从限定字表及面板声明计算所需空格，既不把新版输出当真值，也不声称测过真实终端字体。两种面板组合由实验者构造，不是两个真实生产分布或 48 个缺陷。

- **A 采用新适配器：** 用 0.3.0 默认窄宽处理两列。
- **B 回退：** 用 0.2.14 和既有的宽字符兼容适配器。对限定的 East Asian Ambiguous 字符加一格，始终宽策略。
- **N 原生：** 在 0.3.0 为每列显式传入其配置的 `ambiguous_width`。和其他方法看到完全相同的标签及配置，没有提前看执行结果。
- **仅限 A/B 的原生路由：** 根据两列在任务契约下是否有相容的一种共同宽度，选择 A、B 或暂缓，不做影子验证。

| 24 份报告 / 面板 | 互补：A/B 各成功一半，从不一起成功 | 重叠：A/B 各成功一半，结果完全同向 |
|---|---:|---:|
| 配对结果 `11 / 10 / 01 / 00` | 0 / 12 / 12 / 0 | 12 / 0 / 0 / 12 |
| 固定 A 或 B 的平均损失 | 0.5000 | 0.5000 |
| 成对全审计 | **0.3500** | 0.5250 |
| 短路审计，A 成功便不再查 B | **0.2625** | **0.4375** |
| 原生路由，只能用 A/B | **0** | **0.1750** |
| 原生逐列指定宽度 | **0** | **0** |

成本是假设单位：错误交付 1，暂缓 0.35，单次影子审计 0.175。全审计每面板 48 次影子执行；短路为 36 次，少 25%。两种都复用经过验证的产物，额外上线执行为 0。全审计、短路在互补面板均正确交付 24/24；重叠面板均正确交付 12/24、暂缓 12、无错交付。原生逐列设置均以 24 次上线执行正确交付 24/24，无影子验证。仅限 A/B 的原生路由在互补面板正确交付 24、重叠面板正确交付 12 并暂缓 12。一次报告执行实际计算两个标签。完全因子矩阵在真实版本上计算，表格是对在线策略的确定性重放，不代表每个策略先免费取得所有结果。

两种面板的 A/B 边际相同，但在固定 0.35 成对审计假设下，联合结果确实改变 **A/B 固定 versus 成对验证** 的选择：互补需验证，重叠选固定。在可以短路时，两种都低于固定策略，说明结论依赖审计实现。只用历史动作边际的对比明确抹去了公开面板配置；存在这个配置时，强原生策略有无须审计的自然解。**这是实际 API 上的反例检验，不是联合核验算法的立项信号。**

## 复现

```sh
mkdir -p wheels releases
for v in 0.2.14 0.3.0; do
  python3 -m pip download --no-deps --only-binary=:all: -d wheels wcwidth==$v
  python3 -m zipfile -e wheels/wcwidth-$v* releases/wcwidth-$v
done
sha256sum -c LOCK.sha256
(cd wheels && sha256sum -c ../WHEELS.sha256)
python3 -B scout.py releases | diff -u aggregate.json -
```
