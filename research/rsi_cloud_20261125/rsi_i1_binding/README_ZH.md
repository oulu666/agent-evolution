# I1：把正确数值写到正确对象

Windows 笔记本已连接。检查已有 WSL 环境时返回 `Wsl/E_ACCESSDENIED`，未启动所需的 Qwen3-0.6B。没有绕过权限、安装、下载权重或用别的模型替代。下面是云端完成的功能筛查，**不包含小模型或真实 Agent 成绩**。

每案用真实内存 SQLite 为模拟分页得到正确上限，三个同名导入记录同时存在。所有方法拿到相同的上限、调用来源和修订信息。合法修复必须作用于同一个、唯一且仍是当前修订的记录。证据重复但同源可去重；证据过期、缺失或冲突一律暂缓。独立判据比较整个数据库状态，不只看某条上限是否正确。

| 100 案，40 应修复、60 应暂缓 | 正确修复 | 上限正确但改错对象 | 不应修却写入 | 正确暂缓 |
|---|---:|---:|---:|---:|
| 总改最后一个记录 | 9 | 31 | 60 | 0 |
| 跟最后一条来源记录 | 40 | 0 | 40 | 20 |
| **唯一来源与修订证书** | **40** | **0** | **0** | **60** |
| **同信息的原生 SQLite 键连接** | **40** | **0** | **0** | **60** |

60 个换 ID 留出案上，证书与原生均正确修复 24、暂缓 36。前者相对弱策略的优势来自唯一性与当前修订检查，原生查询也能直接做到。每案上限读取一次，最多一次写入；不对墙钟速度、真实错误率或研判大模型的能力作结论。所有案例是合成的数据状态，不是自然历史缺陷。

**判断：** 绑定到 `(调用、对象、修订)` 是合理的提交守卫，但这份证据还不支持核心算法立项。真正的 TinyAgent 命题仍未测：在同样看到正确上限与来源的前提下，显式绑定是否能让模型少修错对象、而不是仅提高格式正确率。

## 后续已有本地 Qwen 的接口

```sh
python3 -B run.py export-prompts > prompts.jsonl
python3 -B run.py score-responses < responses.jsonl
```

每个提示记录有 `case`、`mode`、`prompt`、`do_sample` 和 `max_new_tokens`。在已有本地 Qwen3-0.6B 上用其聊天模板、关闭 thinking、贪心解码，从新生成词开始截取答案，每个提示只生成一次。不要用评分器或合成案例真值辅助模型。将实际生成文本作为 `response` 字段收集，每行的 `case`、`mode` 照抄提示 ID；不清理格式或重复提交。评分器会把漏跑或格式错单独计数，报告正确修复、正确值但绑错对象、乱写和暂缓。共 30 个不同任务、raw/neutral/bound 每模式各 30。绑定版新增确定性解析结果，不是与原版相同的认知成本，也没有声称三者 token 数完全一致。此接口目前仅做过程序级自检。
