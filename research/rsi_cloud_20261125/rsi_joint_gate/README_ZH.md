# 修复互相覆盖：组合候选的准入实验

**结论：真实库行为产生了冲突，但这组任务没有可用来证明新算法优势的空间。** 不升级为新的算法方案。

## 实验

三个工具分别实际构造、序列化并读回文件：openpyxl 3.1.5（单元格字体与数字格式）、lxml 6.1.1（XML 节点文本与属性）、PyYAML 6.0.3（块布局与键顺序）。每种工具四种配置，每种配置八份文档，共 96 个场景。故意覆盖可交换、单向覆盖（两种方向）、双向覆盖四类。每个场景检查两个目标及一个已有内容保留条件。单项修复确实能达到自己的目标。

库行为依据：[openpyxl 样式](https://openpyxl.readthedocs.io/en/stable/styles.html)、[lxml clear](https://lxml.de/apidoc/lxml.etree.html#lxml.etree._Element.clear)、[PyYAML 序列化](https://pyyaml.org/wiki/PyYAMLDocumentation)。交互由适配器配置构造，不能当作开源历史缺陷、真实版本迁移或独立留出集一直统计。八份文档复用同一配置，不是八个独立机制。

| 比较 | 正确交付 | 说明 |
|---|---:|---|
| 固定 A→B | 48/96 | 部分被后写覆盖 |
| 固定 B→A | 48/96 | 换顺序只挽救相反方向 |
| 事后挑能通过的顺序 | 72/96 | 24 个两种顺序均失败 |
| 按对象字段直接合并 | 96/96 | 每场景一次完整写出和读回 |
| 先 A→B，再 B→A，最后用字段合并 | 96/96 | 168 次完整写出和读回 |

例如两次分别赋给同一单元格不同的 NamedStyle，后一次会覆盖先前的字体或格式。状态事实不是“每次随机出现”，而是下层 API 的整体写入语义。直接设置字体与数字格式，保留单元格原值，就一次完成了两个目标。XML 和 YAML 也可在同一个对象或一次序列化中合并。因而这个实验支持“冲突真实发生”，同时排除了“必须用更聪明的排序策略才解决”。

## 下一道门槛

只接受真实迁移任务中经独立确认的冲突：局部修改可以保住各自的检查，但同一个显式字段合并或文档规则不能解决。诸如需要横跨多个工具的共享状态、无法单独写回字段、检查依赖不可见中间状态，才是候选条件；这些条件需要上游证据，不能只删除强基线的权限来人为制造收益。再用同权限、同调用预算比较字段级合并、组合搜索和候选机制。

## 复现

从本文件所在目录运行 `python gate.py --out results`。依赖版本见 `requirements.txt`。公开分支不保留逐条判定；可运行本地复现脚本生成。实际实验证据是在 Python 3.12.14 下执行，不涉及 GitHub 仓库原有代码或本地 GPU。
