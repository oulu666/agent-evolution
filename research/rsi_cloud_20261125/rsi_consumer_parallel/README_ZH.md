# 用合法下游消费者区分相同的最终产物

在云端 Linux / Python 3.12.14 运行。已有面板记录过 attrs 的回调参数问题。本次复用这个已知缺陷，验证同一回调的实际业务后果，并增加一个独立的标准库语义对照，不声称发现新缺陷。

- **attrs 25.3.0 → 25.4.0：** 给包裹构造器传估值 200，默认值是 100。两版序列化的成品对象都为 `{"estimate":200}`；合法的构造前回调把收到的估值交给预留任务（阈值 150），旧版选择 `hold`，新版选择 `reserve`。业务判据独立使用调用方明确传入的 200。普通终值检查和构造后检查都漏掉这个差异。对应 [官方变更记录及 #1427](https://www.attrs.org/en/stable/changelog.html)。
- **Python Decimal：** 对 `100.201` 真实四舍五入到分，和直接构造已算好的 `100.20`，产生相同的完整 Decimal 三元组。要求“舍去非零数位则送审”的消费者沿用该次运算的上下文，从 [公开 Inexact 标志](https://docs.python.org/3.12/library/decimal.html#decimal.Inexact) 得到 `review`，绕过真实运算的路径选择 `release`。这是同一库的实际 API 路径，不是缺陷或版本切换。

## 实验

每域 16 个设计可区分的输入与 8 个不应有差异的控制；总计 48 案，检查了所有可选观察位置，48 案的两份最终产物均一致。类型导向绑定从业务任务指定的输入类型反推现有接口，例如“构造请求”映射到构造前回调、“算术信息损失”映射到 Inexact。这个原型只做类型匹配，并没有自动从文档发现接口。原生强基线直接在同一个公开接口上挂接同一业务决策。

| 策略 | 阳性观测正确区分 | 阴性对照误报 | 成对调用次数 |
|:---|---:|---:|---:|
| 只核对产物或结束后等价处理 | 0/32 | 0/16 | 96 |
| 类型导向消费者 | 32/32 | 0/16 | 48 |
| 原生文档消费者 | 32/32 | 0/16 | 48 |
| 穷举三个观察位置 | 32/32 | 0/16 | 144 |

每个成对调用执行两个路径。矩阵先在两版真实 attrs 和标准库上完整运行，随后按策略离线计算所需调用；未把建表成本藏成线上收益。三种有消费者定位能力的策略找到同一观察位置和工作流，原生在一个成对调用就达到上界。阳性/阴性由设计者构造，不是 48 个独立历史缺陷。

**决定：** 候选消费者可真实暴露最终产物遮蔽的差异，但只要任务已经说明要读哪个公共事件，原生做法就同效、同价。不把类型匹配立项为核心算法。如果继续，应先找一批独立缺陷，其工作流由领域契约规定、却不能直接知道要从哪个允许的端口或合法组合取得证据，再比较最短状态机与原生路线。

## Replay
在本目录运行：

```sh
mkdir -p wheels releases
for ver in 25.3.0 25.4.0; do
  python3 -m pip download --no-deps --only-binary=:all: -d wheels attrs==$ver
  python3 -m zipfile -e wheels/attrs-$ver-py3-none-any.whl releases/attrs-$ver
done
sha256sum -c LOCK.sha256
(cd wheels && sha256sum -c ../WHEELS.sha256)
python3 -B scout.py releases | diff -u aggregate.json -
```

复跑 Python 3.12 的其他补丁版本时，仅顶层 `python` 字段预计不同。
