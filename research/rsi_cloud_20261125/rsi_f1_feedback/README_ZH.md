# F1：同预算配对反馈能否让修复迁移？

云端未具备可用的小模型运行时或缓存权重。本次只是**有限规则的可执行信息量筛查**，没有训练、微调或提示 LLM，不能外推到 Qwen3-0.6B。真实执行 Python Decimal 舍入与 SQLite 排名。任务契约预先从有限集合指定；有的验完整产物，有的只验其中一项。修复器知道候选契约词汇和操作结果，但不知道正确契约；通过所见反馈排除不相容规则，再选用于新输入的动作。

同种子共享两个成功锚点，各组共四条五字节记录（20 字节；不是模型 tokenizer 的 token）。配对组补两个同输入的失败动作，随机成功组补两个新输入上的成功动作，破坏配对组保留失败动作与标签但对调输入绑定。精筛成功组以离线额外筛选为代价，挑最能收缩剩余假设的两个成功例，只作强信息上界。复制对照在随机成功组里直接复用最常见动作。成功/失败条目来自预先穷举，主实验共构建 448 个真实 API 候选产物；等反馈记录不等于从环境取得反馈的总成本相同。

| 方法 | 正确 / 768 | 错误 | 暂缓 |
|---|---:|---:|---:|
| 随机成功例中直接复用常见动作 | 664 | 104 | 0 |
| 同输入成功–失败配对 | 658 | 14 | 96 |
| 破坏配对 | 373 | 11 | 384 |
| **同记录预算，随机成功例** | **712** | **3** | **53** |
| 离线精筛成功例的强上界 | 765 | 0 | 3 |

- 完整验收的 48 个种子块中，失败侧 **48/48** 未进一步排除假设：知道同输入下一个成功动作的完整执行结果，就已知道同输入每个候选输出是否相等，不需要额外失败标签。
- 部分验收的 48 块中，失败侧在 Decimal 的 13 块提供额外约束，在 SQLite 的 24 块未提供。增加约束未转化成相对同预算随机成功组的胜利，后者在四个面板都正确交付更多。
- 配对组在 42 个无法直接复制成功锚点的新案例里解决 5 个；**固定同样 42 个由共用锚点定义的案例**，随机成功组解决 24，精筛成功组解决 42。这排除了用不同分母夸大迁移收益。随机成功例解决案例可能直接复用额外成功演示，因此仅配对组的 5 个直接说明没有复制本组任一成功锚点。
- 破坏配对在 96 个种子块中造成 42 个不一致记录集，程序按预定规则暂缓；这是刻意注入错误输入绑定的压力对照，不能用来宣称真实模型普遍依赖 pair 结构。

**决定：** 不立项“开放式配对反馈天然比同预算成功例更能自进化”。先验理论只支持“部分判据下，真实失败动作有机会带来新的限制”，本轮还没有交付率的优势。新输入改变数值范围、顺序和数据形状，任务语义/接口不变，不能称跨项目泛化。精筛上界可看到训练真契约以挑正例，其成本不与线上的两条补充记录混算。
