# 多观测关联：单点无法判断，双点能恢复对象身份

本次验证同一个问题在两个真实库接口上的表现：

- **SQLite 3.53.1：** 用户任务是刷新库存记录但保留旧引用。真实 `UPDATE` 和 `INSERT OR REPLACE` 可交付相同的 SKU 和值；替换路径在测试中明确选择另一个 rowid，因而不保留旧行引用。不是说所有 `REPLACE` 必然改变 rowid。
- **ElementTree：** 修改元素正文和移除后创建新元素产生逐字相同的 XML。已经订阅旧对象的消费者却需要知道发布后的树是否仍包含原来的对象；独立注册表把两个真实对象映射到不透明句柄。

每个块都有两种初始身份 A/B，分别执行保留或替换一次。替换时交换 A/B。这样，在每个观测点，正负例的值分布**严格相等**。但前后两次身份观测之间的相等关系可区分语义。不是“两个单独结果都逐对完全相同”；相同的是各自的条件边缘分布。

## 策略与结果

每域 12 个开发块、12 个同结构留出块，每块四样本。留出块换用未见过的身份、SKU、正文；生成逻辑并未换域。这不是历史缺陷或独立样本统计。候选从六个允许的观察位置选择，不预先指定正确钩子；候选和基线均可在两个同类型观测之间比较相等/不等、一点时拟合观测值表。声明类型如“句柄”是双方共享的公开信息。开发阶段使用完全观测，留出调用数按选中的观测数重放统计，两者均单独计量。

| 策略 | 留出正确 / 96 | 留出观察次数 | 两域拟合规则数 |
|---|---:|---:|---:|
| 最好的单点规则，甚至允许用留出标签反向拟合 | 48 | 96 | 不适用 |
| **开发集单点边缘平衡剪枝，搜索双点** | 96 | 192 | 4 |
| **同文法精确最短观察子集** | 96 | 192 | 16 |

两种搜索均选择“更新前身份”和“发布后身份”；每域 48/48，均为每案 2 个观测。剪枝把拟合规则数从 16 降为 4，但统计各点边缘分布还有计算开销；未测到任何端到端运行收益，也没有减少线上观察。每域每个开发样本的每个观察都已取得，即 288 个预计算观察值，双方共享。统计单位是观察值而非 SQLite 事务或 XML API 调用，总 SQL/XML 运行成本并非 192 条。

**结论：** 两点关联确实能让合法消费者分辨终值相同的更新，静态边缘平衡可证明一个点不够；但最短子集已经以相同成本达到结果，候选只提供局部剪枝，不推进算法立项。下一步若继续，应冻结不同项目上未知的跨阶段关系，要求真实独立任务，以及把学习和执行总成本同时纳入强对照。
