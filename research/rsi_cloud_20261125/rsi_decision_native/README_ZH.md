# D 分支：事务续行、核验或回滚

在云端 Python 标准库真实执行 SQLite 3.53.1。每案例尝试创建一张库存预留单，必须满足数量非负、仓库存在以及任务约定的总量限额。每种策略使用新建的内存数据库，不调用真实仓储服务。SQLite 的 [延迟外键](https://www.sqlite.org/foreignkeys.html#fk_deferred) 能在尝试提交时自动拒绝无效仓库，但不会自动检查这里的业务总额。

候选把各约束归入证实、证伪、由数据库提交保障、待核验四类：已证伪则回滚，有剩余义务则核验，否则续行。强原生策略不构建证据状态表，直接使用同一事务的现成总量和数据库原生原子保证，只检查剩余业务限额或未强制的外键。两者知道的现场信息相同，都看不到尚未核验的仓库存在性或总量值。

| 策略 | 正确持久结果 / 57 | 错误落库 | 显式核验查询 | 组合留出正确 / 25 |
|:---|---:|---:|---:|---:|
| 插入没报错就尝试提交 | 39 | 18 | 0 | 15 |
| 每次显式核验 | 57 | 0 | 72 | 25 |
| **证明状态门控** | 57 | 0 | 40 | 25 |
| **同信息的强原生策略** | 57 | 0 | 40 | 25 |

候选和原生的动作数也完全相同：续行 17、核验 34、直接回滚 6；续行或核验后有 12 次由数据库拒绝提交并执行回滚。两种无错误策略在留出组合各用 20 次额外核验。每个策略获得同样 30 次共享快照查询；这些已计量但不混入 40 次追加核验。没有宣称节省墙钟时间、训练量、调用 LLM 或测试独立历史缺陷。

初始数据的已有库存总量（限额组）是常数，可能诱发捷径。冻结的稳健性复跑把同一可见限额和提案数量配上不同真实库存，且留出使用新数量/限额组合。复跑汇总与初始实验逐字节相同。隐藏总量的某些状态确实无法直接判定：在没有自定义原子业务验证、起始快照和额外读取时，相同输入可能对应应提交或应回滚。这个下界适用于该分离式接口，而非任意 SQL；若允许数据库触发器或带业务谓词的联合写入，可重新设计接口。

**决定：** 核验仅剩不确定性比每次全量核验省 32 次，但是强原生直接实现已经做到完全相同。没有发现候选在现有信息与事务接口上的独立收益，冻结 D 分支，不把它包装成新算法。
