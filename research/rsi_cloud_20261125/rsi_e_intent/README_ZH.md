# E 分支：只追问会改变这次交付的歧义

两个真实库的功能任务：Python `Decimal.quantize` 输出保留一位小数的账务报告，规则可能对中点舍入与负数余额有不同要求；SQLite 窗口函数生成排名名单，规则可能在并列和缺失成绩上不同。用户只用冻结好的有限规则模拟，并根据自己的规则给出一个小例子的预期输出。本实验没有调用 LLM，也没有联系或对真实用户做测试。

候选先用真实 API 计算各候选规则可能给出的结果。一个问题的价值按“若两条规则会生成不同的最终报告，用户对这个小例子的回答能否把它们分开”评分，而不是尽量猜全套规则。比如，正式排行没有缺失分数时，追问缺失分数是否入榜不能改善交付。所有受限方法看到相同的候选规则、先验和例子，并执行相同的成本门槛。强对照直接穷举每个问题，在期望错误、暂缓和问题成本上找最优的一步决策。

| 方法 | 正确 / 168 | 误交付 | 暂缓 | 提问次数 | 总损失 |
|---|---:|---:|---:|---:|---:|
| 默认直接执行 | 84 | 84 | 0 | 0 | 84.0 |
| 不问，按当前信息交付或暂缓 | 54 | 10 | 104 | 0 | 46.4 |
| 最大化全部意图的熵减 | 102 | 10 | 56 | 72 | 36.8 |
| **最大化会影响交付的分歧对切分** | **132** | **4** | **32** | **108** | **26.0** |
| **同菜单的一步最优决策** | **132** | **4** | **32** | **108** | **26.0** |
| 用户直接指出整份报告，超出小例子问答的上界 | 168 | 0 | 0 | 140 | 14.0 |

成本是假设单位：误交付 1、暂缓 0.35、追问 0.10。候选在 Decimal 的模板/变换两组各 31/48，在 SQLite 的模板/变换两组各 35/36，逐组与强对照汇总一致。它相对全意图熵减降低设定损失 29.3%，但多问 36 次；四次误交付集中在一次小例子不足以识别当前组合规则时。所有方法对“每个意图都产生同一结果”的场景多问 0 次；这是成本门槛的机械保障，不是模型懂得所有真实歧义。每一“案例”是报告与一个模拟意图的组合，不能作为独立用户或历史证据。

**决定：** 保留实用策略：先看歧义是否改变当前交付，再决定是否追问，不必恢复完整意图。冻结候选算法，新打分没有超过一步最优的同信息基线。这个实验不测量提问的理解难度、用户可能不答、规则覆盖不足、API 调用成本和真实交互效用。脚本预先执行候选规则形成小矩阵，线上只向模拟用户提一个问题；计算矩阵不是免费预测，未证明其成本可接受。
