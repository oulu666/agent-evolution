# 方法三深化：从公开对象自动发现被动观察点

**结论：可自动发现真实公开接口字段，但字段结构排序不足以从少量读取找到关键观察点。成功域也没有击败简单对照。**

本试验不把正确观察点发给学习器。公共对象的属性列表与公开构造函数形参提供候选根，读取安全的被动数值、元组、字符串和字典叶字段；不调用任意方法，不自动挂钩回调。Decimal Context 的公开构造签名列出可能不在 dir 中显示的字段；这说明工程上不能只扫描 dir。前置校准和冻结记录见 PROTOCOL、FREEZE_NOTE。

对每个候选，学习“读到的值 → 该任务要走的业务路径”映射。若同一值在校准已对应不同决策，则拒绝；未见值时暂缓。三种有预算限制的方法各最多读取三个候选：字母顺序、任务词重叠、以及字段类型优先再按任务词排。字段形状从同一批无标签对象发现；校准标签由业务任务、输入生成逻辑预定，不读目标字段作为真值。额外比较完整扫描一致性和读指定公开观察点的专家控制。完整接口对象早已获得，以下读数是算法观测选择，不是重新执行工具；不声称降低真实端到端调用。

## 实测

Decimal 和 Pillow PNG 实际执行。四任务每种 12 个用于校准、48 个变化值用于评分；逐对验证终值或同尺寸像素哈希相同。干扰字段校准时与标签相关、评分时脱钩。不是独立历史缺陷。

| 方法 | 正确 / 192 | 错误 | 暂缓 |
|---|---:|---:|---:|
| 只看终值/像素 | 0 | 0 | 192 |
| 字母排序 | 72 | 24 | 96 |
| 任务词排序 | 96 | 0 | 96 |
| 形状加任务词排序 | 96 | 0 | 96 |
| 完整扫描，候选预测须一致 | 96 | 0 | 96 |
| 专家指定公共观察点 | 192 | 0 | 0 |

形状法在 PNG 的 3 个候选中成功从文档对象找到 info.dpi、info.workflow，但词排序同样成功。在两个 Decimal 任务里均能列出 24 个候选，但预算 3 的排名没读到 flags.Inexact 或 flags.Rounded。扩大到全扫描，在干扰字段与真正字段冲突时，保守一致性每任务只给 24/48；所以“发现字段”也不等于“知道谁能作判据”。完整扫描的失败属于这个具体学习器，不证明任意完整扫描无效。

公共行为参见 [Python Decimal 信号](https://docs.python.org/3.12/library/decimal.html#signals)、[Pillow PNG 元数据](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#png)；已有[模型驱动测试判据策略](https://ieeexplore.ieee.org/document/7529115/)也研究状态检查位置。真正的深化应自动跟随产物或对象跨调用的业务关联，并独立证实该证据不受表示干扰；静态猜字段名字无法解决。

复现：Python 3.12、Pillow 13.0.0，目录中运行 python pilot.py --out results。在上一级执行 sha256sum -c rsi_observer_discover/LOCK.sha256。逐条数据不进入公共 Git。
