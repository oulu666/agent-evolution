# 第二项检查何时值得做？文档发布工作流的准入审计

2026 年 11 月 25 日

**阶段决定。** 在本次工作流中，修复依赖足以决定检查顺序。先检查源文档，在页面过期时跳过旧压缩包检查，比反向顺序少做 24 次检查。标准两步信息价值规划从开发数据选出了同一条规则。两者在全部 48 个留出情形中都采用了事后完整信息会选的修复动作。DCEP 保持冻结，本轮结束这条工作流上的方法开发。

## 数据、任务和权限

用户需要同时获得当前英文 README 的 HTML 页面和解压后与该页面一致的 gzip 文件。使用 Python 3.11.9、markdown-it-py 4.2.0 的 CommonMark 设置和 Python gzip。两件交付物都实际写入本地。独立进程从当前源文档生成参考页面，评分器回读文件并通过 zlib 检查压缩内容。该判据验证相对指定渲染器的交付一致性；两个进程共用同一渲染引擎。

事前固定一个发布流程。开发集取 Python-Markdown 最近 18 个 README 修订，留出集取 Rich 最近 36 个修订。按时间顺序分成互不重叠的三个修订一组。每组令缓存页面来自中间修订，当前源文档取中间或后一修订，已有压缩包取中间或前一修订。保留四种组合。Rich 共 12 组、48 个情形。Git 提交、渲染、压缩和交付均为真实执行，两个发布步骤的滞后比例由实验控制。项目间使用的是同一个工作流，执行器没有调用语言模型。

| 权限 | 可读取的验证证据 |
|---|---|
| 交付端 | A 读取当前源文档的内容指纹，与 HTML 构建时保存的源指纹比较。B 解压现有 gzip，与缓存 HTML 逐字节比较。 |
| 可读取构建记录 | 同样可用 A、B。另可用 J，一次读取源匹配状态，并比较 HTML 生产者与 gzip 生产者独立记录的 HTML 内容指纹。 |

J 依赖可信构建端提供的记录；本轮共为 Rich 的 36 个修订计算两份额外指纹，合计 1.292 ms。记录驻留内存。这个数包含指纹计算，不包含持久化、分发或验证独立发布者的开销。交付端条件没有这种权限。一次逻辑检查和一次网络往返之间没有预设换算。标准库接口见 [Python gzip 文档](https://docs.python.org/3/library/gzip.html)。

## 对照与算法

各策略均可直接复用两个产物、使用缓存 HTML 重新压缩，或重新渲染当前文档再压缩。最多做两次检查。无条件全量重建是保障正确性的零检查基线。固定顺序允许发现页面过期就直接重建，另设无条件取齐两项证据的对照。

标准两步规划在当前已有证据下比较两种开销。一种是立即采取有充分证据支持的动作。另一种是支付检查成本后，按各返回分支的概率加权计算最优后续成本。递归深度为二，共四种布尔状态。检查及修复成本使用开发集操作耗时中位数；状态权重来自开发集，每种状态加一平滑。决策树在运行留出项目前生成并缓存。规划模型使用平均意义上的操作成本；报告另列含两份文件落盘的真实部署耗时。

事后上界知道当前输入的参考 HTML 和真实 gzip 内容，免费取证，在相同三个终局动作中选择开发集成本最低且可交付正确的一项。本次成本排序为复用、重压、全重建。因此还可直接核对所选动作是否做了多余的渲染或压缩。

## 留出结果

每行均对应同一批 48 个 Rich 情形。三轮打散策略顺序，每个情形取耗时中位数再求和。未设置暂缓动作。各策略的线上成本包括决策树执行、所用检查、修复和写两份文件。预构建产物、一次性校准和离线评分排除在外。

|---|---:|---:|---:|---:|---:|---:|

| 交付端，全量重建 | 48 / 0 | 0 | 48 | 48 | 24 | 342.456 |

| 交付端，两项均查后决策 | 48 / 0 | 96 | 24 | 36 | 48 | 193.029 |
| 交付端，先查源文档，页面过期即重建 | 48 / 0 | **72** | 24 | 36 | **48** | **192.240** |
| 交付端，标准两步规划 | 48 / 0 | **72** | 24 | 36 | **48** | 192.850 |

先查源文档在 12 组中的 7 组比反向顺序快。逻辑检查减少 25%，两种顺序的累计时间只相差 0.621 ms；节省检查的事实不支持稳定的 25% 墙钟加速。减少多余重建的影响更大。相对全量重建，先查源文档少渲染 24 次、少压缩 12 次，累计少用约 150 ms。标准规划与先查源文档逐情形的检查、返回分支和修复动作完全相同。

## 一个可以复查的分支

Rich 的缓存页面来自 d39643d1。如果目标仍是这一修订，而 gzip 来自 709613e4，检查 A 通过，B 发现旧包解出的内容不同；只需压缩缓存 HTML。若目标已更新为 014d8fa9，保留同一个缓存页面及同一个旧包，A 立即发现页面过期。此时直接渲染并压缩新页面，旧包与旧页面是否一致已不影响交付。第一种情况执行 A、B，第二种只执行 A。

## 为什么检查数还有一个可核对的下界

在交付端可用 A、B 的菜单中，要正确区分三个事后动作，首次检查至少一次。若先查 A，24 个页面过期情形可立即重建；其余 24 个必须查 B 才能区分复用与重压。因此最少 48 + 24 = 72 次。若先查 B，无论返回什么，只要 A 未知，都有对应的两个实际状态要求不同修复，48 个情形都要继续查 A。四种有效状态在留出集中各出现 12 次，且首次选择之前没有可按情形区分这些状态的策略输入。读取可信构建记录时，一次 J 就能区分终局，48 次即可。这个下界以保持全部事后修复动作、当前观察权限和事前信息为条件；只要求最终正确时，全量重建可用零检查完成。

因此，事后上界与可部署策略的差距只剩观察当前状态的代价。这个差距不能当作一个新策略可随意回收的预算。

## 四项准入判断

| 判据 | 本次结论 |
|---|---|
| 两项检查是否无法廉价合并 | 取决于权限。交付端规定的菜单中两项提供不同证据；构建指纹可读时，一次联合比较已足够。没有对所有外部接口作排除性证明。 |
| 是否引向不同修复 | 是。留出任务中复用 12 次、只重压 12 次、重新渲染并压缩 24 次。 |
| 顺序是否改变工作量 | 是。交付端可以避免 24 次旧包解压检查。 |
| 是否留下独立于固定规则、精确缓存和标准规划的收益 | 本轮没有。两种权限下，最简单的有效规则与标准规划轨迹一致，并逐项达到事后最少修复。 |

当前结论适用于可信的本地构建链、同一版本的确定性渲染器及注册的交付动作。项目重放频率不代表线上故障率。研究上应保留此次“先算修复上界，再量取证成本”的评估结果；这批发布任务上的 DCEP 扩展到此结束。
