# 从旧版公开文档生成检查，能发现示例遗漏的违约吗？

2026 年 11 月 25 日 · ESWA 新方法单轮准入实验

**决定。** 冻结本轮轻量合成器。两个格式化工具的六对版本上，它在 79 条可执行文档示例之外生成了 63 条检查实例。新增实例全部在父版本和修复版本同时通过。交付环节四种策略都正确交付 140 次、错误交付 0 次、暂缓 4 次。没有取得进入 ESWA 方法开发所需的增量检出或任务收益。

## 入组、揭盲与分析单位

两个本轮首次用于方法设计的项目为数字拼写库 num2words 与 URL 短标识生成库 python-slugify。事先固定项目、分支头、文件和筛查顺序。程序检查 42 条提交元数据，取每个项目最近三条满足修复关键词与文件条件的普通提交。设计者在冻结之前只读取父版本 README 的使用说明和示例；冻结内容包括样本、文档、生成器、基线、检查、交付任务和评分答案。冻结指纹可本地复核。生成器会读取各项目的旧版文档，属于对修复内容设盲、针对当前文档设计的原型，并未测试整套生成器在完全未参与设计的新项目上的泛化。

揭示后，num2words 有两条为 PEP8 风格整理。另四条涉及行为。分别记录文档冲突、两版同败和未观察到的变化。六个入组提交对不能算六个已证实的独立违约。每个项目有 12 个固定用户请求，24 个不同请求在 12 个软件快照上形成 144 个任务情形。项目内的重复文档与重复输入保留在计数中。

两对早期版本在 Python 3.11 无法从当时的公开入口调用。首次运行错误记录在案；揭示后以 PyPy 2.7 原样运行这两对，现代控制器、冻结输入、期望和决策规则相同。原运行和兼容运行分别保存。Python 3 环境使用 Unidecode 1.3.8，Python 2 环境使用 0.04.21；每个父子版本对使用相同依赖。[事前协议](contract_synthesis_gate/protocol.md) · [筛查记录](../runs_contract_synthesis_gate_20261125/screening.json) · [冻结指纹](../runs_contract_synthesis_gate_20261125/lock.json)

## 算法与基线

生成器先把旧版文档中的交互示例和“输入赋值 → 调用 → assertEqual”解析成文字常量、参数、关系与行号。随后用一个人工定义的小型关系集合生成可执行检查。它识别默认语言、区域语言写法与未支持语言的异常约定，还从多个示例中归纳长度、停用词和分隔符关系。比如，只有同一输入、其他参数相同、两个输出按各自分隔符切开后词序列完全相同时，才会对一个新分隔符生成精确预期。每个检查都保留文档行号与证据类型。

本轮观察位置限于公开函数的返回值与异常。这次没有合成生命周期钩子，也没有调用语言模型。对照包括固定类型检查、直接文档示例和 Hypothesis 驱动的通用属性测试。后者测试了数字拼写的基本输出属性，以及默认 ASCII 短标识的重复规范化；Hypothesis 负责生成输入，属性由研究者提供。直接示例基线也支持 README 中的普通断言，覆盖面比只识别提示符更广。本轮没有运行专门面向其他语言或 REST 接口的契约合成系统。[检查生成器](contract_synthesis_gate/compile_checks.py) · [Hypothesis 官方说明](https://hypothesis.readthedocs.io/en/latest/quickstart.html)

| 检查来源 | 跨六份父版文档的实例数 | 父版本失败、修复版通过 |
|---|---:|---:|
| 文档给出具体输入和答案 | 79 | 0 |
| 明确文字条款生成的新检查 | 15 | 0 |
| 区域语言解释归纳 | 9 | 0 |
| 两个示例对照归纳的分隔符替换 | 9 | 0 |
| 长度、停用词示例归纳 | 30 | 0 |

新增 63 条实例包含两类明确文字要求和四类归纳关系。同一要求换输入或出现在多版文档中会产生多条实例。48 条归纳检查能追溯到示例，示例对其适用范围的支持弱于明文契约。直接示例、包含示例的合成器和通用属性基线在六个父版上的离线调用分别为 79、157、216 次，三组均未检出父失败、修复通过的版本对。[带文档行号的全量检查](../runs_contract_synthesis_gate_20261125/checks.json)

## 交付层

同一交付控制器接收指定函数和参数，得到真实工具返回后交付或暂缓。各策略每个任务最多一次主调用加一次验证。直接示例策略优先核对完全匹配的示例，否则执行参数最接近的例子；合成策略优先使用当前任务适用的关系，缺失时走同一基线。期望答案只交给离线评分器。它测量的是 Agent 的工具交付层。

| 策略 | 正确交付 | 错误交付 | 暂缓 | 实际工具调用 |
|---|---:|---:|---:|---:|
| 固定类型检查 | 140 | 0 | 4 | 144 |
| 通用属性检查 | 140 | 0 | 4 | 168 |
| 直接文档示例 | 140 | 0 | 4 | 272 |
| 契约合成 | 140 | 0 | 4 | 246 |

四次暂缓来自同一早期接口缺少 stopwords 参数，涉及两项任务各跑父、子版本。四种策略逐任务交付结果相同。合成器比文档示例少调用 26 次。固定类型基线已经没有错误交付可供减少，这批任务对第三道门槛没有可测的正收益空间。结果不能估计合成器在有错误交付的生产任务上的效果。[评分汇总](../runs_contract_synthesis_gate_20261125/summary.json) · [原始运行](../runs_contract_synthesis_gate_20261125/observations.json) · [历史运行时结果](../runs_contract_synthesis_gate_20261125/compatibility_observations.json)

## 阶段评价

第一项门槛部分达到。轻量程序能自动编译两类明确条款，并在公开示例支持下生成更多可执行检查。第二项未达到。没有新增历史违约检出。第三项未取得正证据。简单基线已正确处理所有成功返回的冻结任务。

本轮冻结，不据揭示结果追加组合模板、不重新计分。能用于后续研究的两项判据是：测试输入是否覆盖契约同时生效的条件，以及断言是否有足够独立的依据识别两个调用共同产生的错误。现有结果支持把这两项纳入契约到测试的实证分析；没有支持把该合成器列为 ESWA 核心算法。
