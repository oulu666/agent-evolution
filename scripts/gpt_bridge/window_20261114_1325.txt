三、现存的核心问题
我认为现在主要有四个瓶颈。
瓶颈 1：不知道什么经验真正有效
目前已经知道：
• 特定 target 经验有价值；
• 普通同工具经验不一定有效；
• 近邻操作模式可能产生额外收益。
但我们不知道如何在训练之前预测这些收益。
这是最核心的科学问题。

例如：
filter_top 的经验能否帮助模型完成新的 filter_count？
search_first 的经验能否帮助模型完成 search_last？

虽然已经找到 db.list_tables 和 py.median 的真实遗忘证据，但目前 E3-B2 的主要实验对象仍是原本没有掌握的 filter_cmp_top。
因此还没有完整证明：
模型原本掌握技能 → 学习新工具后遗忘 → 自适应 Replay 重新恢复。
瓶颈 4：实验规模和评测仍然有限
• 只有一个 0.6B 模型。
• 主要是 A 场景。
• E3-B2 实验 A 目前只完成种子 08。
• Calendar v3fix 的工具选择准确率固定在约 50%，区分能力不足。
• 部分模式存在天花板或地板效应。
这些都限制了目前结论的外部有效性。

为什么提前出现会有效？
可以把模型想象成一个正在学习编程的学生。
你让他复习一道 SQL 查询题。
如果在考试前最后一刻才复习，他虽然看到了这道题，但后续几乎没有训练过程让这次学习继续影响参数。
如果提前复习，后面还有更多训练更新，目标经验对最终参数状态的影响就可能更充分。
这里并不是同一道题被重复训练了四次。
而是：
同一道训练经验出现一次，但它出现得更早，训练剩余阶段有更多优化更新。
这正是本轮实验最重要的机制线索。

五、目前整个研究到底在做什么？
我把整个研究重新串起来。
你现在研究的不是普通的工具调用，也不只是让 Agent 记住更多 API。
你的问题是：
一个智能体不断学习新工具、新操作时，如何用有限的历史经验，维持和恢复它已经获得的工具使用能力？
这属于 Continual Tool Learning（持续工具学习）。
1. 先理解我们要解决的问题
假设有一个小模型，它需要依次学习三种工具：

问题来了：
模型学会 File、Calendar 之后，可能出现：
• 原来会的 Database 操作不会了；
• 某些 API 还记得，但参数构造错误；
• 相似操作之间容易混淆；
• 训练过程中获得的新能力可能影响旧能力。
这就是持续学习里的灾难性遗忘及技能迁移问题。
传统 Replay 的做法很简单：
从历史经验池拿出一些旧样本，和新任务一起训练。
但是这里有两个问题：
1. 应该拿哪些历史经验？
2. 应该把这些经验放在训练序列的什么位置？
我们之前主要研究第一个问题。
这轮实验开始回答第二个问题。
2. 目前研究已经形成了怎样的技术路线？
目前的研究演进
E1：发现技能恢复问题
研究不同工具学习阶段的能力变化，发现一些操作模式出现能力缺口和真实遗忘。
E2：建立 Replay 剂量实验
比较不同目标经验数量和复习比例，发现目标模式的恢复具有明显的剂量响应关系。
E3：研究经验身份和覆盖
研究 Target 经验与普通工具背景的差异，发现单纯增加普通 Database 背景没有带来预期增益。
E3-B2：控制经验背景
进一步比较 Target-only 和 Target + Database Background，初步排除了普通同工具背景的解释。
本轮新增
P2：研究 Target Timing 和 Exposure
控制经验数量、训练预算和内容，改变 Target 插入位置，发现更新时间暴露是解释恢复效果的重要变量。
下一阶段：Exposure-Aware Replay
根据技能缺口和经验价值，自动决定复习什么、复习多少、何时复习。
这条研究路线现在已经比较清晰了。
之前我们想解决的是：
如何选择值得复习的经验？
现在进一步发现：
选择经验之后，还必须考虑如何安排它在训练过程中的位置。
未来真正的方法应该同时解决这两个问题。
3. 我认为目前最有价值的科学故事
可以把你的论文核心逻辑整理为：
问题： 现有 Replay 方法往往重视历史经验的数量、采样比例和覆盖情况，却没有充分考虑经验在训练序列中的时间位置。
观察： 同一条 Target 经验，提前插入和最后插入，会产生明显不同的恢复结果。
机制假设： Target 的更新暴露量影响其对最终模型参数的作用程度。
方法： 设计一种感知技能缺口和更新暴露的 Replay 调度策略。
目标： 在固定 Token 和训练预算下，用更少的历史经验恢复更多目标技能，同时减少其他技能退化。
这里最重要的是：目前的实验支持前面的观察和机制假设，但还没有实现最后的方法。

模块四：Adaptive Stop Controller
什么时候停止复习？
如果某项技能已经恢复，就不应该继续无意义地消耗训练预算。
停止条件可以是：
• 目标技能达到预设准确率；
• 连续几轮验证收益很小；
• 其他旧技能出现明显退化；
• Replay 预算已经用完。
这样就构成真正的闭环自适应学习。

至少要有：

5. Early Target Replay：固定提前插入。
6. Exposure-Aware Replay：根据技能缺口安排暴露量。
7. Adaptive Replay：进一步根据经验预测收益动态分配预算。

• 总训练时间；

第三步：正式提出自适应 Replay 算法
这是未来论文真正的方法创新。
我建议暂时命名为：
EAAR：Exposure-Aware Adaptive Replay
整体流程：
模型学习新工具
￼
监测细粒度技能变化
找出真正退化的技能
￼
选择高价值历史经验
考虑技能缺口与经验覆盖
￼
自适应安排 Replay
每条经验的暴露量 + 不同经验的覆盖面
￼
重新评测并调整
判断是否继续复习
￼
形成持续学习闭环
第一版不需要强化学习，也不需要教师模型。先做规则驱动的自适应调度，再和 Random Replay、Uniform Replay、Fixed Replay、Early Replay 比较。
七、我对目前研究进度的最终判断
目前已经取得的成果
• 发现定向经验复习可以明显修复细粒度工具能力缺口。
• 发现经验出现太晚，可能来不及产生足够的后续更新收益。
• 发现单条经验的暴露存在收益平台，多条不同经验可能扩大覆盖范围。
• 发现 Arguments 和 Final 的表现可能受到不同经验分配方式的影响。
• 初步建立了 Exposure-aware Replay 的方法设计基础。
还没有完成的成果
• 经独立验证的饱和暴露模型。
• 真正的遗忘恢复实验。
• 自动选择经验和安排时机的完整算法。
• 多技能、多工具、跨模型验证。
最后，我认为研究故事应该升级成这样
以前的研究问题是：
小模型忘记旧工具后，能不能通过 Replay 恢复？
现在可以进一步提出：
小模型在持续学习中，应该如何分配有限的复习预算？什么时候复习一条经验？什么时候应该放弃重复复习，转而覆盖更多不同经验？
我认为这比单纯研究 Replay 数量更有研究价值。
而且有一个很重要的判断：
P3 已经让我们看到，真正值得研究的可能不是「复习多少次」，而是「有限的训练机会应该如何在不同历史经验之间分配」。
这就是未来 EAAR 最有潜力的核心。
我建议当前的执行顺序锁定为：CPU 建立饱和覆盖模型 → GPU 验证真实遗忘 → 设计并预注册 EAAR → 多种子和多工具验证。
不要急着扩展模型规模。先把这个机制在 0.6B 模型上证明清楚，再考虑迁移到更大的模型。
