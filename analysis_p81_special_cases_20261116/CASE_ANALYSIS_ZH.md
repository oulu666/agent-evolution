# P8.1 特殊错误案例与研究决策

依据：已完成的 P8/P8.1 原始输入、输出、数据库和 CPU 变体结果。本次仅做存档分析，新增模型调用 0 次，不修改冻结成绩。逐例证据见同目录 evidence.json，可由 scripts/audit_p81_special_cases.py 重新提取。

## 决策

主线收敛到：经验怎样使模型在任务规则改变时相应改变输出，在无关呈现改变时保持规则。先校正评测条件，再以固定上限的小型推理探针选择训练干预；随后优先做 File 单因素训练。暂缓扩大种子、模型规模、联合经验包和梯度收益分配器。

## 1. 改 first/last 不改答案，倒转列表却改答案

种子 20261109，p81-file-0，匹配原文件第 2、4 行：

|呈现|要求|实际输出|
|---|---|---|
|2→4|first|entry 2: p81key0 value p81_0_2|
|2→4|last|entry 2: p81key0 value p81_0_2|
|4→2|first|entry 4: p81key0 value p81_0_4|
|4→2|last|entry 4: p81key0 value p81_0_4|

自然表达的这种行为覆盖全部 6 个文件、3 个种子。输出对无关显示位置敏感，对真正决定答案的意图变化不敏感。可直接证实行为层的位置依赖，不能由此声称已经定位到某个注意力头或内部机制。

训练目标要同时要求：同一任务换显示顺序答案不变；同一文件 first 换 last 时答案正确改变。单看 last 倒序成功会奖励原来的错误策略。

## 2. 更简单的两项题反而失败

显式要求最大行号、正常顺序时：2 个匹配项 0/6，3 个匹配项 6/6，4 个匹配项 5/6。种子 09 的 case0（2、4 行）选 2，case1（2、4、6 行）选 6。

更特殊的是，P8 实际选中的所有 File first/last 训练题均为 2 项，last 终点评测为 4/4。故“两个候选本身超出能力”不成立；熟悉格式与新格式的迁移很可能比题目长度更关键。不过项数和 case 文本同时变化，当前分组不是项数的独立因果实验。

File 探针采用每个种子一个实际学过的配对文件为起点。6 个条件：原题、只换路径/检索标记等标识、只改指令措辞、只改变原文件行位置、只倒转返回列表、只增加一个匹配项；每条件 first/last 各一题。共 6×2×3=36 次答案生成。每个条件独立相对原题改变一个因素，标签随真实文件语义重新计算。探针仅选择干预，不作为最终独立测试集。

## 3. 两个简单 SQL 都会，组合后丢失其中一条

种子 09，p81_zero：

单独筛选：SELECT name FROM p81_zero WHERE score > 50，正确。

单独排序：SELECT name FROM p81_zero ORDER BY score DESC LIMIT 4，正确。

筛选加排序：仍生成 SELECT name FROM p81_zero ORDER BY score DESC LIMIT 4，丢掉 WHERE。

该表没有合格记录，正确返回应为空，实际返回四个名字。这清楚地区分了查询能执行与任务条件满足。行为符合“使用熟悉查询模板时未保留全部条件”的解释；不能直接推断模型完全缺乏组合能力，因为同一模型结构化表达能生成正确组合查询。

下一步 SQL 经验使用相邻任务对，每次只增加/删除一个约束，评分检查该约束引发的输出变化。先处理调用阶段和 schema 条件，再决定是否值得新增 SQL 训练。

## 4. 错误规则也能得到完全正确的返回值

种子 09，p81-db-ties-filter_sort_tie-natural：

实际 SQL：SELECT name FROM p81_ties ORDER BY name ASC LIMIT 4。

它漏筛选、漏分数排序、用名字代替 id，却通过原实例语义检查。原因是该表全部记录同分且合格，名字又编码了 id。已有三个 CPU 变体中它全部失败。

后续数据需让 name/id/score 独立变化，并加入不合格记录、score=阈值、超过 top-k 的并列记录。单个实例返回正确只是实例正确，不足以证明规则正确。无需为此重复生成模型答案，先对现有查询重执行即可。

## 5. 结构化提示有时把工具调用变成凭空作答

种子 08，p81-db-zero-filter_sort-structured 输出 {"answer": ["zero"]}。正常流程应先生成 db_query。种子 08 的 12 个结构化条件均失败，但自然表达的单筛选/单排序成功。

结构化题的末尾为 Return names as a JSON list.，而系统要求第一回合输出工具 JSON。这句与 natural 条件的变化一起出现，可能诱发阶段混淆；当前没有独立消融证明它是原因。把这些失败统称为 SQL 组合能力不足，会选择错误训练目标。

## 6. 本次发现的评测条件问题

### 系统 schema 陈旧

P8.1 的 24 个 SQL 输入，系统提示均列 employees/sales/products；真实数据库只有 p81_zero/p81_few/p81_ties，用户题目给出这些新表。P8 新题也继承了这份旧系统描述。

来源：data/generate.py 的 build_system_prompt 使用静态 FAMILY_CONTEXT，data/templates.py 固定声明旧库。数据库工具定义随环境创建，并不意味着系统中的数据库文字同步更新。

因此此前“沿用 employees 是训练记忆干扰”的解释不充分：当前上下文本身就在提供 employees。需要动态生成真实 schema，或删去静态表清单；用旧提示和一致提示在同模型上配对，才能估计它解释多少失败。这个问题不会自动解释已经观察到的 File 行为或新表上漏 WHERE 的全部错误。

### 等价 SQL 和输出接口要求混在一起

已确认省略默认 ASC 的正确查询被严格字符串匹配误判。

本次进一步发现种子 09 的 p81-db-ties-sort-structured：SELECT name AS v FROM p81_ties ORDER BY score DESC LIMIT 4。返回值及顺序与参考一致，仅列名为 v；语义评分器强制 columns == ['name']，因此判失败。

该失败应描述为列标签契约不符，不能说排序不会。若最终任务只要求名字列表，应分别报告值语义与接口契约。不能机械地把所有别名错误放宽为正确：同种子的 zero-sort-structured 按 v（即名字）排序，只在原数据上碰巧与分数同序；列标签归一化后它也会通过原实例，但规则仍有问题。

## 7. 固定范围的推进方案

1. CPU 整理：动态 schema 方案、调用阶段明确的模板、语义/接口/最终答案分层指标。冻结历史结果，另建新协议。
2. 最多 72 次新的推理诊断：File 上述 36 次；SQL 选 4 个代表条件×3 个提示版本×3 种子=36 次。SQL 版本依次为旧提示、仅校正 schema、校正 schema 后仅明确当前回合必须先调用工具。选条件覆盖自然/结构化表达、单操作/组合及已观察到的阶段错误，不再铺满原矩阵。只在相邻版本间归因相应改动。
3. 根据 File 响应选一个训练因素。若主要是顺序敏感，B 仅改训练观察的呈现顺序；若主要是措辞/格式迁移失败，B 仅改对应经验表达或表面标识。A 复用 P8 Decision，不重训。B 三种子从相同前缀训练；固定 first/last 次数、其余经验及更新次数，记录实际 token 成本。不要同时改顺序、措辞、loss 和预算分配。
4. 用全新文件与表达做终点测试。主指标为正常工具链 last，关键配对指标为同文件两种意图、两种顺序四个输出全部正确；报告每种子配对差值与 first 副作用。只有未见题上的规则收益出现，才开展独立 SQL 训练或收益分配器实验。

## 8. 核心算法的研究对象

经验价值应由规则响应测量：

- 不相关变化 T：f(Tx) 应等于原正确答案（例如仅换呈现顺序）。
- 任务规则变化 C：f(Cx) 应等于新的正确答案（例如 first→last，SQL 增加 WHERE）。

对每个基础任务建立对照小组，计算组内所有规则检查都通过的比例 G(theta)。候选经验的短更新收益采用 [G_dev(Update(S,a)) - G_dev(Update(S,background))]/总成本，而非只看训练损失或单题正确率。这个分配器仍是待验证设计；先证明所选择的经验能改善 G，才有理由优化预算选择。

关键研究问题由“多复习是否有效”收敛为“哪些经验让模型学会对相关变化作响应、对无关变化保持不变，以及怎样低成本选择这些经验”。
